- **全局作用域盘点**：18 个头 + 20 个 .cpp 完全无 namespace；176 个手写中文技能类（+3 CRTP 基类 = 179）、1226 个 `X::` 成员定义、Card/Character/Effect/GameLogic/Player/MessageType/协议 DTO/适配器具体类/ref·opt_ref 均在全局；全局符号引用 **4414 处 / 77 文件（89 文件中的 87%）**。加命名空间的技术障碍：7 个 `std::formatter` 特化、20 处全局 `sf::Packet` 运算符、2 个 `NLOHMANN_JSON_SERIALIZE_ENUM` + 10 个 `DEFINE_TYPE_INTRUSIVE`（ADL 在全局找 to_json/from_json）、24 个全局前向声明、`Card.h:77` 成员函数指针 bit_cast。冲突实证 **0 起**：dep/ 无同名类型、无 `using namespace std`、唯一同名 `Key` 已命名空间化、0 处 `::` 规避痕迹。
- **结论：不建议全量命名空间化**。命名空间不产生架构边界（B+ 的边界是编译单元 / 头文件闭包 / 构造注入），0 冲突 = 0 当前收益，却要全面触碰冻结区；真正没理顺的是已有 8 个命名空间语义不一致，而非「缺命名空间」。触发门槛：安卓立项 → 只把共享契约值类型（Card 值类型 / CharacterTypes / TableConfig / Key / player_id）归入 `unool::contract` 并升独立编译单元；规则引擎要作为库被外部链接或引入同名第三方库 → 才给规则主体加 `unool::` 并用别名桥接（须专门处理 formatter / ADL / 宏）；CI 落地 → 才考虑把 `player_id` 升级为强类型。若只嫌命名别扭，唯一值得做的是把 `Player::id` + `getId()` 改成 `player_id` 共 2 行、零行为变化，**不要扩成全量**。
- 已按用户指令执行该 2 行：`header/application/Player.h:28` 与 `:105` 改用 `unool::domain::player_id`；`getId()` 仅 inline 定义、20 个调用点全按 size_t 使用，别名替换零影响；构造参数 `_id` 仍是 `std::size_t`（同一底层类型，无转换）。`Types.h` 由本头已直接 include 的 `IDecisionPort.h:7` 传递提供，按「两行」口径未加第 3 行显式 include（若将来 `IDecisionPort.h` 去掉该包含，需补 `#include "domain/Types.h"`）。源码与工程文件仅此一处改动，未提交。
